# テストの削除・統合

判断基準は **「削除すると、どんな現実的な不具合を見逃すか」** の一点。件数・カバレッジ率の維持は目的にしない。「念のため」は残す理由にならない。実行時間・不安定さ・修正負担と、保証の価値を比較する。

## ワークフロー

1. **テストを全件列挙し、実装と対で読む**
   ```bash
   find . -path ./node_modules -prune -o \( -name "*.test.*" -o -name "*.spec.*" -o -name "*_test.*" -o -path "*__tests__*" \) -type f -print | xargs wc -l | sort -n
   ```
   テストだけ読んで判断しない。必ず対象の実装（分岐・throw・境界）を見て「このケースは実装のどの行を守っているか」を特定する。
2. **テストスイートを実行し、所要時間を把握する**（削減の価値を測る材料になる）
3. **各テストを下記の分類で判定し、リストアップして報告する**（実装前にユーザーへ提示）
4. 承認後、ブランチを切って反映 → テスト・lint 通過を確認 → 1 コミットで PR

## 削除対象の分類

| 分類 | 見分け方 | 例 |
|---|---|---|
| 実装のコピー | テストが実装と同じ式・同じ定数表を持つ | 定数配列を再列挙して照合 |
| モックの自己検証 | モックが返した値をそのまま assert | `mock.returns(x); expect(fn()).toBe(x)` |
| 型・ライブラリの保証 | TS の型や標準ライブラリが既に保証 | `Array.isArray` の挙動確認 |
| 他テストとの重複 | 別テストがその経路を必ず通る、または throw で担保済み | 存在チェック（未知キーで throw する関数の順序テストがあれば不要） |
| 内部実装への依存 | 挙動を変えずにリファクタしただけで壊れる | 「同一オブジェクトを返す（コピーしない）」 |
| 過剰なケース分け | 実装に分岐がないのにケースを増やしている | 1 行の `a && b` に対して 3 色 × 2 ルール |
| 条件が緩く保証がない | ほぼ何が来ても通る assert | `accepted <= declared`（0 件でも通る） |

## 残すべきもの

- 過去の実バグに対応した回帰テスト（コメントに issue 番号や経緯があるもの）
- 境界値（`<=` vs `<`、`0` を falsy と誤判定、範囲外入力、不正要素のスキップ）
- フィクスチャを使った end-to-end 的な再生・整合テスト。低コストで最も広い保証を持つことが多い
- 統合時も「独自の保証を持つ行」は捨てず、統合先のテストへ移す（例: 一意性チェックを別テストへ移動）

## 報告フォーマット

```markdown
**全体の所感**: ファイル数・件数・実行時間と、全体の質の評価

## 削除を推奨
- **ファイル/テスト名** — なぜ保証がないか。どのテストが代わりに担保しているか

## 統合を推奨
- **ファイル/テスト名** — 何と何を 1 件にするか。実装上分岐がない根拠

## 残すべきと判断したもの
- 削らない理由を明示（回帰テスト、境界値など）

**まとめ**: N 件中、削除 X 件・統合で Y 件減。これ以上削ると失う保証
```

「残すべきもの」も必ず書く。削減の下限を示すことで、過剰な削除を防ぎユーザーが判断しやすくなる。

## コミット・PR

コミットメッセージと PR 本文は「削除」「統合」「残したもの」の 3 セクションで、各項目に **代わりに何が担保しているか** を 1 行添える。件数の推移（例: 48 → 34）と、テスト・lint の通過を明記する。
